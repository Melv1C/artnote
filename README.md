# ArtNote

ArtNote is a [TanStack Start](https://tanstack.com/start) application that publishes scholarly notices about paintings for a French-speaking audience. It uses Prisma on a PostgreSQL database, MinIO for uploaded images, and Better Auth for authentication. It is self-hosted on Dokploy (`docs/adr/0011-self-hosted-on-dokploy.md`).

## Setup

1. Use the correct Node.js version:

   ```bash
   # If you have nvm installed
   nvm use

   # Or install Node.js 24 manually
   # The project requires Node.js 24 (see .nvmrc)
   ```

2. Install dependencies with [Bun](https://bun.com) (version pinned through `packageManager` in `package.json`). Bun is only the package manager and script runner; the app itself runs on Node.js:

   ```bash
   bun install
   ```

   Dependency lifecycle scripts only run for packages listed in `trustedDependencies` (currently just `esbuild`). Prisma's postinstall is skipped on purpose; the client is generated by `db:setup`, `check`, `prisma:migrate` and the `Dockerfile`.

3. Environment variables: `bun run db:setup` (next step) writes `.env` from `.env.example` on its first run, with a database and dev port of its own for this checkout. `.env` and `.env.local` are loaded into `process.env` for server code (`.env.local` wins). The variables are validated in `src/lib/env-schema.ts`. Image uploads go to the local MinIO that `db:setup` starts (console at http://localhost:9001, user `artnote`, password `artnote-dev-storage`). A `.env` written before MinIO was added lacks the `S3_*` variables: copy them from `.env.example`.

4. Start the local database and MinIO (Docker), create this checkout's database and the shared `artnote` bucket, apply migrations, generate the Prisma client and seed sample data:

   ```bash
   bun run db:setup
   ```

   Sign in with `admin@example.com`, `writer@example.com` (a second admin), `user@example.com` or `banned@example.com` (refused), password `artnote-dev-password`. Staging has the same accounts with other passwords (AGENTS.md, Environments and QA). `db:setup`, `db:reset` and the seed refuse to run against a non-local database.

5. Run the development server:
   ```bash
   bun run dev
   ```
   The app is served at `BASE_URL` from `.env`.

## Scripts

- `bun run dev` – Vite dev server with TanStack Start.
- `bun run build` – production build (client assets and the Nitro server output in `.output/`).
- `bun run start` – serve the production build locally (`node .output/server/index.mjs`).
- `docker build .` – the production image Dokploy builds; the container runs `prisma migrate deploy`, then the server on port 3000.
- `bun run check` – everything CI runs: Prisma generate, validate and format check, `vp check` (Oxfmt, Oxlint and the TypeScript type check), `vp test` (Vitest), knip and the build (regenerates `src/routeTree.gen.ts`).
- `bun run fix` – format and apply lint fixes.
- `bun run db:setup` / `db:seed` / `db:reset` / `db:down` – local database and MinIO: set up, re-seed, recreate this checkout's database, stop the shared containers.

## Deployments

Dokploy, on our own server, builds the `Dockerfile` from GitHub (ADR 0011):

| Environment | Address                         | Deploys on                                                  | Database and MinIO |
| ----------- | ------------------------------- | ----------------------------------------------------------- | ------------------ |
| Production  | https://artnote.melvyn.be       | a push to `production` (only the Release workflow moves it) | its own            |
| Staging     | https://stg.artnote.melvyn.be   | a push to `main`                                            | its own            |
| Preview     | a `*.artnote.melvyn.be` address | a PR from this repository labelled `preview`                | staging's          |

Uploaded files are served from https://files.artnote.melvyn.be (production) and https://files.stg.artnote.melvyn.be (staging and previews). Every container runs `prisma migrate deploy` before it starts, so a preview's migration reaches the staging database (ADR 0006). Deploys don't wait for CI.

To release, tag a commit that is on `main` and push the tag:

```bash
git tag v1.2.0 origin/main
git push origin v1.2.0
```

`.github/workflows/release.yml` force-pushes the tagged commit to `production`, which Dokploy deploys, and creates the GitHub Release. To roll back, push a tag on an older commit, or redeploy an earlier deployment in Dokploy.

Each Dokploy app sets these variables (`src/lib/env-schema.ts`): `BASE_URL`, `PRISMA_DATABASE_URL`, `BETTER_AUTH_SECRET`, `CRON_SECRET`, `CLIENT_IP_HEADER=x-real-ip`, the five `S3_*` variables, and `UMAMI_WEBSITE_ID` in production only. Previews get staging's values; Dokploy adds `DOKPLOY_DEPLOY_URL`, which replaces `BASE_URL`. A Dokploy schedule on production and staging calls the nightly cron from inside the container:

```bash
node -e "fetch('http://localhost:3000/api/cron/prune-view-records',{headers:{authorization:'Bearer '+process.env.CRON_SECRET}}).then(r=>r.text()).then(console.log)"
```

A new MinIO gets its bucket from `scripts/storage/init-bucket.sh` (public reads, no listing). There are no automatic backups.

## Toolchain

[Vite+](https://viteplus.dev) (`vp`) is the toolchain: Vite for dev and build, Vitest for tests, Oxlint for linting and Oxfmt for formatting, all configured in `vite.config.ts`. `vp check` formats, lints and type-checks in one pass. knip covers unused code. See `docs/adr/0008-vite-plus-toolchain.md`.
